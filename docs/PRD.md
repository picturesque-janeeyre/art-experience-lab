## 1. 한 줄 정의

미술 전문 저술가의 미술 인문학·감상 콘텐츠와 저서·교과서를 소개하고, 수강 후기로 신뢰를 쌓아 **강연·집필·교육 프로그램 의뢰를 받는** 개인 브랜드 사이트.

- 사이트 이름: 미술 경험치 연구소 / ART EXPERIENCE LAB [확정]
- 슬로건: 그림을 만나고, 취향을 발견하고, 생각을 남기다. [확정]
- 작가 소개 한 줄: 미술 전문 저술가 · 미술교육 전문가 · 미술 인문학 콘텐츠 기획자 [확정]
- 사업적으로 가장 중요한 목적: **강연·출강·집필·교육 프로그램 의뢰 접수** [확정]

### 핵심 사업 흐름 (모든 화면 설계의 기준)

```
그림과 콘텐츠로 관심을 끈다 → 책과 교과서로 전문성을 보여 준다 → 수강 후기로 신뢰를 쌓는다 → 의뢰를 받는다
```

## 3. 손님이 궁금한 것 (연락하기 전에)

기관 담당자 기준:
1. **이 사람이 이 주제를 맡길 만한 전문가인가?** (학력·저서·교과서 집필·교육 경력)
2. **우리 대상과 상황에 맞는 프로그램이 있나?** (대상·내용·진행 방식·시간)
3. **실제로 들은 사람들 반응은 어땠나?** (승인된 수강 후기)

→ 세 가지 모두 의뢰 버튼 **바로 위**에서 답할 수 있게 배치한다.

## 7. 폼에서 받을 것 — 폼 두 개를 반드시 구분한다

두 폼은 **다른 페이지, 다른 저장 표, 다른 관리 화면**을 쓴다. 한 폼에 섞지 않는다.

### 7-1. 수강 후기 폼 (`/voices/write` → 표: `reviews`)

| 항목 | 필수 | 형식 |
|---|---|---|
| 참여 강연 또는 프로그램 | 필수 | 선택 목록 (7개 + '기타' 직접 입력) |
| 참여 시기 | 선택 | 연·월 |
| 한 줄 후기 | 필수 | 100자 이내 |
| 기억에 남는 점 | 선택 | 300자 이내 |
| 표시 이름 또는 별명 | 선택 | 20자 이내, 비우면 "익명 수강생" |
| 후기 공개 동의 | 필수 | ○ 사이트 공개에 동의합니다 / ○ 공개하지 않고 작가에게만 전달합니다 |

- 이름·연락처·이메일·학교 이름은 **받지 않는다**. 개인정보를 모으지 않는 폼이라서 개인정보 수집 동의 칸은 두지 않고, 공개 동의만 받는다.
- 안내 문구: "실명이나 연락처 등 개인을 알아볼 수 있는 내용은 적지 말아 주세요."
- 저장할 때 상태는 항상 `대기`로 시작한다.

### 7-2. 협업 의뢰 폼 (`/contact` → 표: `inquiries`)

| 항목 | 필수 | 형식 |
|---|---|---|
| 기관명 | 필수 | 텍스트 |
| 담당자 이름 | 필수 | 텍스트 |
| 이메일 | 필수 | 이메일 |
| 연락처 | 선택 | 전화번호 |
| 의뢰 유형 | 필수 | 미술 인문학 강연 / 학교 출강 / 교사 연수 / 저자와의 만남 / 원고 집필 / 교과서 및 교육 콘텐츠 집필 / 미술교육 프로그램 개발 / 기타 협업 |
| 희망 일정 | 선택 | 텍스트 (예: 11월 중 평일 오후) |
| 참여 대상 및 예상 인원 | 선택 | 텍스트 |
| 희망 주제 | 선택 | 텍스트 (프로그램·도서에서 들어오면 미리 채움) |
| 예상 예산 | 선택 | 선택 목록 또는 텍스트, "미정·협의" 포함 |
| 의뢰 내용 | 필수 | 긴 텍스트 |
| 개인정보 수집·이용 동의 | **필수** | 체크박스 + 수집 항목·목적·보관 기간 안내 펼쳐 보기 |

- 자동 스팸 방지: 사람 눈에 안 보이는 함정 칸(허니팟)과 같은 사람의 연속 제출 제한. CAPTCHA는 1차에 넣지 않는다.

## 8. 정확해야 하는 사실 (사용자가 말한 그대로)

- 가격(강연료): 사이트에 공개하지 않음, "협의" (공개 여부는 추후 확인)
- 시간·위치: 해당 없음 (출강형, 일정은 의뢰마다 협의)
- 연락 방법: 사이트 의뢰 폼 → 운영자 이메일로 알림 → 이메일로 회신
- 공개 연락처(이메일 직접 노출 여부): (미정)
- 저서 6권 · 교과서 2권 · 근간 1권: 제목·출판사·연도는 4-3 그대로. 표지는 추후 제공
- 작가 이름: 김수정 (실명) · 현직 교사 언급 없음
- 강연·선정·칼럼·방송 이력: 4-4~4-6 그대로 (표현을 바꾸거나 부풀리지 않는다)

### 2차 이후 비전 메모
- 취향 테스트는 **심리 진단이 아니라 감상 교육 경험**으로 쓴다. 결과 문구에 "당신은 ~한 사람입니다" 같은 단정을 피하고 "~한 그림에 끌리는 편이에요"처럼 쓴다. 색채·구도·소재·분위기 4개 축으로 본다.
- 오늘의 그림은 작품 한 점을 위 6단계 흐름으로 감상하는 긴 세로 스크롤 페이지로 만든다.
- 3차 개인화 기능은 회원가입이 필요할 수 있다. 그때 개인정보 처리방침을 다시 검토한다.

### 12-2. 기술 구성
- 화면: 정적 HTML/CSS/JS (책·강연 정보는 `data/*.json`에서 읽는다)
- 저장: **Supabase** — 표 2개 `inquiries`(문의), `reviews`(후기) (leaderpl-admin 스킬 기준)
- 서버 기능: Vercel `/api` 함수 (폼 접수, 공개 후기 조회, 관리자 기능)
- 알림: 새 문의(필수)·새 후기(권장)가 들어오면 **운영자 이메일로 알림**. 메일 발송 서비스(예: Resend)를 쓰고, 가입과 키 입력은 사용자가 직접 한다.
- 관리자: `/admin`, 비밀번호(ADMIN_PASSWORD) 하나로 잠근다. 관리 범위는 **문의·후기 관리만** [확정]
- 회원가입: 이번엔 아니요 [확정]
- 배포: GitHub 공개 저장소 + Vercel
- 비밀 값(Supabase 키, 메일 키, 관리자 비밀번호)은 저장소에 올리지 않고 Vercel 환경 변수에만 둔다.

### 12-3. 개인정보·공개 동의·접근 권한 기본 요구사항 (Must)
1. **두 폼 분리**: 후기에는 개인정보를 받지 않고, 문의만 개인정보 동의를 받는다.
2. **후기가 공개되는 조건**: `공개 동의 = 예` **그리고** `관리자 상태 = 승인`일 때만 공개한다. 공개에 동의하지 않은 후기는 승인 버튼이 나오지 않는다.
3. **바깥에서 읽을 수 없게 막기**: 방문자 브라우저는 Supabase 표를 직접 읽거나 쓰지 않는다. 모든 접근은 `/api`를 거친다. 공개 후기 API는 승인 후기의 표시용 칸(한 줄 후기, 기억에 남는 점, 프로그램, 시기, 표시 이름)만 돌려준다. 문의 표는 관리자 API로만 읽을 수 있다. Supabase 행 단위 보안(RLS)을 켜고, 익명 사용자의 읽기 권한은 주지 않는다.
4. **관리자 접근**: `/admin`과 관리자 API는 비밀번호 확인 후에만 쓸 수 있다. 검색엔진 수집 금지(noindex)를 걸고 메뉴에도 보이지 않게 한다.
5. **개인정보 처리방침**: 수집 항목(기관명·담당자 이름·이메일·연락처), 목적(의뢰 회신과 협의), 보관 기간, 파기 방법, 문의처를 적는다. 보관 기간은 [추후 확인] (제안: 처리 완료 후 1년, 이후 삭제)
6. 접속 IP 같은 추가 식별 정보는 저장하지 않는다. 스팸 제한은 잠깐만 쓰고 저장하지 않는다.
7. 이미지 권한: 작품 이미지는 **저작권이 만료된 작품이나 사용 허가를 받은 이미지만** 쓴다. 출처와 소장처를 캡션에 적는다. 책 표지는 출판사 사용 허락을 확인한다. [추후 확인]

### 12-4. 겸직·복무 관련 메모 [추후 확인 — 사용자 책임 영역]
- 현직 교사이므로 강연료·원고료 등 수익 활동은 소속 기관의 겸직 허가와 복무 기준을 따라야 한다. 사이트 문구는 "의뢰"와 "협의" 중심으로 쓰고 가격표를 두지 않는다.
- 사이트 자체에 광고·판매 기능은 넣지 않는다. 구매 링크는 외부 서점으로 연결만 한다.

## 13. 만드는 순서 (Claude가 처음부터 끝까지 한 번에)

1. 12-1 스타일(색·글꼴·여백 규칙)을 정하고 홈 첫 화면부터 만든다.
2. 홈 나머지 섹션 → `/about` → `/library` → `/programs` → `/voices` → `/voices/write` → `/contact` → `/privacy` 순서로 만든다. 실제 자료가 없는 곳은 "준비 중" 자리를 둔다.
3. 휴대폰 화면(360~430px)에서 전체 페이지를 점검한다.
4. GitHub 공개 저장소에 올리고 Vercel로 배포해 사이트 주소를 만든다.
5. 두 폼 → `/api` → Supabase(`inquiries`, `reviews`) 저장 → 이메일 알림 → `/admin`(문의 관리, 후기 승인) 순서로 연결한다.
6. 확인: 테스트 문의와 테스트 후기를 넣는다. 공개에 동의하지 않았거나 승인하지 않은 후기가 바깥에 보이지 않는지 확인한다. 확인이 끝나면 테스트 데이터를 지운다.
7. 다 만든 뒤 한 번에 보고: 사이트 주소 · 관리자 주소 · 후기 QR 주소 · 확인 방법 · 사용자가 할 일
- 사용자가 직접 할 일 (이때만 멈춤): GitHub·Vercel·Supabase·메일 서비스 로그인과 가입, 관리자 비밀번호(ADMIN_PASSWORD) 입력, 알림 받을 이메일 주소 입력
